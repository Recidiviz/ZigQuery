# Benchmark — four BigQuery emulators over the REST API

Generated by `tools/emubench_svg.py --markdown` from `docs/bench/emubench.json`. Re-run the measurement with `uv run tools/emubench.py --out docs/bench/emubench.json`.

## How this was measured

- **Surface**: one `POST /bigquery/v2/projects/proj/queries` per iteration — the synchronous `jobs.query` endpoint, one round trip, connection reused across iterations.
- **Corpus**: the 22 queries of [goccy/googlesqlite's bench corpus](https://github.com/goccy/googlesqlite/tree/main/bench), vendored under `testdata/bench_corpus/`. The queries were not chosen here.
- **Isolation**: a fresh container per (engine, case). The corpus reuses table names with different schemas — `events` has five shapes, `lineitem` four — so a shared container would corrupt results.
- **Storage is equalised to in-memory.** Left at their defaults only two of the four are: `zigquery` uses SQLite's memdb VFS and `bqemulator` opens DuckDB on `:memory:`, while both Go emulators call `os.CreateTemp` and open `file:<tmp>?cache=shared` on the container filesystem — goccy's `--database` flag says "if not specified, it will be on memory", but the code does not. They are therefore launched with `--database=:memory:`, which their own DSN construction turns into `file::memory:?cache=shared`. This correction *helps* the two comparators: it removes a disk round trip from their numbers and none from the baseline's.
- **Platform**: every engine runs as `linux/amd64` with `--cpus 2 --memory 4g`, one container at a time, on Apple M4 Pro (Darwin 25.6.0, Docker 29.1.3). amd64 is emulated for all four equally.
- **Statistics**: 3 warmup iterations discarded, then at least 10 timed iterations and at least 3000 ms per case. The headline is the **median**; under a hypervisor the distribution is right-skewed and a mean tracks outliers rather than the engine.

## What this does not measure

- **Not engine speed.** HTTP framing and JSON encode/decode are inside every number. The `transport_floor` column below is the per-request cost of a REST call that does no query work, and it differs by more than 20x across these engines — so the Scalar category largely measures servers, not SQL.
- **Scale.** Fixtures are 200–5,000 rows generated in SQL, so this measures per-query overhead — analysis, planning, boundary crossings — not scan performance at scale. `emubench-cases` is the suite for that.
- **Not correctness.** An engine returning wrong rows quickly is not faster. Result fingerprints are compared across engines and any disagreement is listed at the end.

## Result agreement

Every engine that answered a query returned the **same number of rows** for it.

8 queries returned matching row counts but differing cell text: `lag_lead`, `cte_session_funnel`, `filtered_lookup`, `priced_orders_report`, `q1_lineitem_pricing_summary`, `q3_shipping_priority`, `q5_local_supplier`, `q6_forecast_revenue`. The REST API renders every value as a string and these engines do not agree on how to format a FLOAT64 or a TIMESTAMP, so this is expected to be formatting rather than a wrong answer — worth a look, not a blocker.


## Divergence from the upstream corpus

Two setup blocks differ from goccy's originals so that their queries return rows. Both **timed queries are byte-identical to upstream**; only the generated fixture data changed.

- `mixed/priced_orders_report` — upstream spreads all 5,000 orders across a single day (`INTERVAL MOD(n, 86400) SECOND`), so the query's `placed_at >= 2024-02-01` filter matches nothing. Now spread over 90 days.
- `tpch_like/q5_local_supplier` — upstream's `o_custkey = MOD(n,500)+1` against `l_suppkey = MOD(n-1,200)+1` makes the join predicate `s.s_nationkey = c.c_nationkey` reduce to `a = (a+1) mod 25`, false for every row. Now `MOD(n-1,500)+1`, which aligns the two derivations.
