# Recidiviz BigQuery Emulator

A local BigQuery emulator server, built on a GoogleSQL and SQLite.


## Why Zig?

The previous Go-based implementations come with a burden of integrating with the GoogleSQL C library.

* Current upstream compiles GoogleSQL to WASM, then transpiles WASM to Pure Go
  * Processes incur a startup cost of loading the WASM 
  * This is too slow for us as memory is managed by the WASM implementation: values live in linear memory, so every field read copies across the boundary, and every accessor returns `(value, error)`
  * The fork's 2,790-line extractor exists to touch each AST node once and copy it out, so nothing downstream re-crosses
  * `encoder.go` hand-writes a "wasm-free equivalent of CastValue" because the natural path runs per cell, per row
  * Re-registering a builtin name *hard-traps* rather than erroring, so the catalog keeps a pre-filter set to avoid it
* Prior to that, CGO was used. A custom amalgamation of header files for all GoogleSQL dependencies had to be managed.
  * 1,378 `extern "C"` bridge functions for the analyzer package alone, over 1,556 vendored `.cc` files
  * Vendoring freezes bugs in place: that tree now needs a curated protobuf file list, `-include cstdint`, a farmhash namespace macro, and exclusions for deps that were never vendored

Zig links C and C++ natively, so the boundary is one call.
* `ResolvedNode::SaveTo` serializes the resolved statement to protobuf and Zig decodes it once — one call, one copy per statement
* `googlesql` stays upstream: a pristine submodule built by its own Bazel, so an upgrade is a pointer move
* RE2 and ICU come out of the same shim, so regex and Unicode semantics match by construction rather than by effort

It is not free: Bazel and a C++ toolchain are still needed for the shim, the dylib is ~53 MB, proto decoding is generated by a script in this repo, and Zig's pre-1.0 stdlib moves between releases.


## What is ported, and what is not

The internal architecture mirrors the Go original — extractor → coordinator →
transformers → SQL object model, the tagged-binary value codec, the
`zetasqlite_*` UDFs and the `zetasqlite_catalog` table.

Two parts deliberately diverge:

- The **driver layer** is redesigned rather than ported (`src/sqlite.zig` +
  `src/driver.zig` over the SQLite C API, in place of `database/sql`).
- The **value codec** is storage format 3, which Go has no equivalent of. Values
  cross the SQLite boundary as native scalars or BLOBs, never base64 text, and
  the encoding of every orderable kind is memcomparable — so SQLite's own byte
  comparison gives GoogleSQL's ordering and there is no collation. Making that
  possible meant giving NUMERIC/BIGNUMERIC the fixed scale their declared types
  imply, where Go keeps an unbounded `big.Rat`; see
  [docs/NUMERIC_FIDELITY.md](docs/NUMERIC_FIDELITY.md) for what that changed and
  what is still off.

## Prerequisites

- Zig 0.16
- Bazel 7.6 + the [googlesql](https://github.com/google/googlesql) submodule
- `googlesql` analyzer shim built
  - `bazel build -c opt //shim:libgooglesql_shim.dylib`
  - or `zig build -Dbuild-shim=true`
- `brew install kcov`, for `zig build coverage` only

## Build & test

```sh
zig build test      # unit tests
zig build corpus    # replay testdata/corpus.json (the go-zetasqlite query_test.go suite)
zig build coverage  # line coverage -> zig-out/coverage/report/index.html

zig build gsql-bench -Drelease=true  # goccy/googlesqlite's bench corpus -> docs/BENCH_GSQL.md
```

`coverage` runs the engine and server unit tests under kcov and merges the two
runs. It builds at `-ODebug` whatever `-Doptimize` says, because optimized line
coverage measures inlining rather than tests. It covers `zig build test` and
`test-server` only — anything reached solely through `corpus` reads as 0%.

The corpus (748 cases) is exported from the Go repo's `query_test.go` by
`corpus_export_test.go` there:

```sh
CORPUS_OUT=$PWD/testdata/corpus.json \
  (cd ~/go/github.com/Recidiviz/go-zetasqlite && go test -run TestExportCorpus .)
```

`testdata/baseline.txt` lists the case names that must pass; `zig build corpus`
exits nonzero on any regression.
